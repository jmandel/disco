# PLATFORM.md — what disco is, and the plan

disco is **one engine + one methodology, pointed at many software systems**, plus the **product packs**
it generates. Two layers: a generic platform that improves over time, and the per-product packs it
produces. This file is the map and the current plan. (How it was *built* lives in `BRIEF.md` /
`DECISIONS.md`; this is about *what it is* and *where it's going*.)

## Layer 1 — the platform (generic, improves over time)

- **Engine** — `src/**`, `cli/**`, `defaults.ts`, `schema.sql`: the daemon (CDP instrumentation,
  settlement, attribution, store), the faces (library + CLI), the vendored selector engine. Knows nothing
  about any product.
- **Reusable software library** — a small, growing set of product-agnostic discovery moves
  (`extract-from-wire`, `open-defensively`, recon + ambient warm-up, write-flag recon) that per-product
  functions lean on. Grows only as a move recurs across products; plain TypeScript, no framework.
- **Methodology & usage docs** — deep documents on *how to use the library to instrument, explore,
  discover, characterize, and automate a website*: the **design philosophy**, and **how to use it
  effectively, with worked examples**. Not how it was built — how to wield it. (Seeded by `GUIDANCE.md`
  §7–8, `README.md`, `demos/`; expanded as its own workstream — see the plan.)
- **Harness** — `gauntlet/**`, `test/**`: a synthetic, deliberately hostile target with known answers,
  used to test the engine and rehearse the methodology.

## Layer 2 — product packs (per-target, generated by Layer 1)

`apps/<target>/`. **Not a template** — a loose home that accretes whatever *ways of knowing* the
product needs. Five shapes a pack can hold (take any subset; packs differ on purpose):

1. **Raw debug sessions** — captured store(s) + blobs; empirical, retroactively re-queryable.
2. **Ledger / notes** — observed-vs-inferred, variability with n-counts, open questions + probes.
3. **Navigation notes** — how to drive it, the rough edges, how to recover, the **known anchor points**
   workflows start from.
4. **A function library** — plain TypeScript: job-specific, robust functions that navigate to anchor
   states and perform specific steps (`login`, `openPatient(pid)`, `goToProblemList`, …). Composable,
   decomposed and refined over time. The growing asset — and the future basis for **MCP / agent tools**
   and for **automated test loops** that run over them.
5. **Evidence** — screenshots, reports, cited act ids / store cursors.

The three instances differ exactly this way, on purpose: `apps/gauntlet/` is script-heavy (a test
target), `apps/openemr/` is understanding+wire-heavy (server-rendered EHR), `apps/saucedemo/` is
DOM-first (a client-rendered SPA with no data API). None is "incomplete against a schema"; each is shaped by need.

**Design principle for the function library (#4):** the engineering goes into **robustness** — handling
rough edges, recovering from problems, reliably reaching known anchor states you can start a workflow
from — **not into file formats**. They are just `.ts` files: plain exported functions with clear
signatures, so wrapping them as MCP tools or running test loops over them later is trivial. No bespoke
config, no DSL, nothing clever about the format itself.

## Runtime — sessions (ephemeral, gitignored)

`sessions/<name>/` = a single run against one target (`store.sqlite` with every event **plus your
`disco note` interpretations**, `blobs/`, `manifest.json`). Notes live *inside* the session store, so
they are scoped to that run, then **promoted** into the pack when distilled. **sessions : product =
many : 1** (the gauntlet pack came from two sessions; OpenEMR from one).

## How the platform compounds

Each learning sorts by altitude: true of the **tool** → Layer 1 code + `DECISIONS.md`; true of **this
product** → its pack (Layer 2); true of the **class / the craft** → the methodology & usage docs. Every
exploration sharpens the platform, not just its own pack. (Full model: `apps/README.md`.)

## The plan (agreed 2026-08-30)

1. ✅ **Name the palette** — the five ways of knowing above, in `apps/README.md`. Not a schema.
2. ✅ **Function libraries + reusable moves** — `lib/` generic moves (`wire.ts`, `nav.ts`); reference
   library on the gauntlet (`apps/gauntlet/lib.ts`); OpenEMR library (`apps/openemr/lib.ts`:
   `login`/`findPatient`/`openPatient`/`extractSummary`) validated live.
3. ✅ **Usage & philosophy docs** — `docs/using-disco.md` (instrument → explore → discover → characterize
   → automate, with both instances as worked examples). Grows as the libraries do.
4. ✅ **Test loops** — per-pack `check.ts` + a one-command runner `scripts/run-check.ts <target>` that
   stands up a fresh browser+session, runs the pack's check, and exits with its status (schedulable).
5. **Later** — ✅ *third instance done*: `apps/saucedemo/` (Sauce Labs, a DOM-only React SPA) proved
   the Layer-1 reusable layer generalizes past wire-rich apps (uses `lib/nav`, no `lib/wire`). Still open:
   MCP / agent-tool exposure of the libraries; deepen OpenEMR (encounter/notes, save-flow); PHI / retention
   posture when a real (non-demo) target needs it (until then: demo / BAA-covered only); the DECISIONS OPEN items.

Sequence so far: **1 → 2 → 3 → 4 done, + 3rd instance (saucedemo).** Three instances now exercise the
platform (gauntlet synthetic, OpenEMR server-rendered+wire, saucedemo client-rendered DOM-only).
